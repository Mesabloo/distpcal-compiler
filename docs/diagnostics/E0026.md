# E0026: type mismatch

A value's type does not match the type expected where it appears.

This is the type checker's general conversion failure: it had an expected type in hand — from a
`@type` annotation, from an enclosing operator's signature, or from an earlier use of the same
name — and the expression it checked does not convert to it. Subtyping and implicit coercions are
tried first; the mismatch is reported only once neither bridges the two types.

## Why it fires

```tla
---- MODULE Example ----
CONSTANTS
    \* @type: Address;
    PID

(*--algorithm Example {
    process (P = PID)
        variables x = "hello";
    {
    l1: x := 1;
    }
}*)
====
```

`x`'s initial value fixes its type to a string, so assigning an integer to it at `l1` has no
conversion.

## How to fix it

- Correct whichever side is wrong: the value, or the annotation that set the expected type.
- If the two types *should* be compatible, check that the value is not narrower than you think — a
  literal's type is whatever the checker infers for it, not whatever would be convenient here.
- If the expected type came from an inferred earlier use rather than an annotation, put an explicit
  `@type` annotation on the declaration, so the mismatch is reported at the line you meant.

## See also

- `E0028` — no type could be inferred at all, rather than two types disagreeing.
- `E0036` — more than one type fits, with nothing to choose between them.
