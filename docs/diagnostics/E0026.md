# E0026: type mismatch

A value's type is not compatible with the type expected at the position it appears in.

This is the type checker's general conversion failure: it had an expected type in hand — from an
annotation, from an enclosing operator's signature, or from an earlier use of the same name — and
the expression it checked does not convert to it. Subtyping is consulted first
(`Elaborator/Subtyping.lean`), so this fires only once no coercion applies either.

## Why it fires

```tla
(*--algorithm Example {
    variables x = "hello";
{
l1: x := 1;
}
}*)
```

`x`'s initial value fixes it to a string, so assigning an integer to it has no conversion.

## How to fix it

- Correct whichever side is wrong: the value, or the annotation that fixed the expected type.
- If the two types *should* be compatible, check the value is not tighter than you think — a
  literal's type is whatever the checker infers for it, not whatever would be convenient.
- If the expected type came from an inferred earlier use rather than an annotation, add an explicit
  `@type` annotation on the declaration, so the mismatch is reported where you meant it.

## See also

- `E0028` — no type could be inferred at all, rather than two types disagreeing.
- `E0036` — more than one type fits, with nothing to choose between them.
